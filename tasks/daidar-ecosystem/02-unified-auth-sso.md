# 02 — توحيد تسجيل الدخول والهوية — SSO

## الهدف والنطاق

هوية واحدة للعميل عبر Daidar Hub وDaidar Store ولوحة الأدمن، مع تمهيد دخول Daidar Flow في المنظومة. توحيد المصادقة لا يعني منح كل حساب صلاحيات كل الأنظمة أو دمج أدوار العميل والأدمن.

## متطلبات المصادقة

- فحص مسارات التسجيل والدخول الحالية وقواعد المستخدمين والجلسات قبل اختيار آلية SSO أو تعديلها.
- تحديد مصدر موثوق ومرجع مركزي لهوية المستخدم ومعرّف ثابت لا يعتمد على اسم المستخدم أو البريد المتغير.
- توفير Google OAuth بتدفق موثوق، والتحقق من state وnonce وPKCE حيث يلزم ومن مُصدر التوكن وجمهوره وانتهائه ومعرّف Google الثابت. لا تثق في الدور أو الهوية القادمة من الواجهة.
- ضبط عناوين العودة والدومينات المسموحة بدقة لكل بيئة، وحماية الأسرار وعدم وضعها في كود العميل أو Git.
- مراجعة استمرار تسجيل الدخول بكلمة المرور للحسابات القديمة والإدارة؛ عدم تعطيله أو تغيير بيانات أصحاب الحسابات دون خطة انتقال معتمدة.

## ربط الحسابات القديمة

- جرد مصادر الحسابات والمعرّفات والبريد وحالته وعلاقة المستخدم بالمتاجر والتراخيص والاشتراكات.
- وضع جدول ربط بين الهوية الموحدة والمعرّفات القديمة بدلاً من حذفها أو استبدالها عشوائياً.
- معالجة الحسابات المكررة وتعارض البريد والحسابات بلا بريد موثق. لا تربط حساباً ذا صلاحية مرتفعة أو تنقل ملكية متجر اعتماداً على تشابه البريد وحده.
- طلب إثبات ملكية الحساب أو دخول حالي موثوق عند ربط حساب قديم، ومعالجة الاسترداد والربط اليدوي وفق سياسة واضحة.
- الحفاظ على ملكية المتاجر والطلبات والاشتراكات والبيانات الحالية وتوثيق القرارات والإجراءات الإدارية اللازمة.

## الجلسات والخروج الموحد

- إدارة الجلسات على جهة موثوقة، مع مدة صلاحية وإبطال وتجديد ملائمين ومنع إعادة استخدام الجلسات الملغاة.
- استخدام Cookies آمنة HttpOnly وSecure وSameSite مناسبة، ومعالجة اختلاف الدومينات دون افتراض إمكانية مشاركة Cookie بين صفحات pages.dev المختلفة.
- عدم استخدام localStorage كمصدر ثقة للهوية أو الدور أو الصلاحيات.
- تدوير الجلسة عند الدخول وتغير الصلاحيات، وإبطالها عند الإيقاف أو تغيير بيانات الاعتماد حسب السياسة.
- خروج موحد من الأنظمة المتصلة، مع تعريف واضح لجلسة الجهاز الحالي مقابل جميع الأجهزة، ومنع التحويل المفتوح أو تسريب التوكنات في الروابط والسجلات.
- تحديد معالجة انتهاء الجلسة وعودة المستخدم لصفحة العمل واسترداد حالة الواجهة دون إجراء عملية محمية تلقائياً.

## الأدوار والصلاحيات وحماية APIs

- تعريف العميل وصاحب المتجر والمستخدم المخوّل لنظام معين والأدمن وSuper Admin وفق النموذج الفعلي.
- تطبيق الصلاحيات في الخادم لكل عملية، مع عزل tenant/store ومنع الوصول إلى بيانات الآخرين حتى مع تعديل المعرفات أو طلبات API.
- الفصل بين إثبات الهوية وصلاحية الاشتراك والإذن الإداري؛ البريد أو تسجيل Google وحده لا يمنح دور الإدارة.
- حماية APIs من CSRF والتحويلات غير الموثوقة وCORS غير المقيد، ووضع قيود مناسبة لمحاولات الدخول والتسجيل والربط.
- تشفير كلمات المرور القديمة بصيغة موثوقة إن استمر دعمها، وعدم كشف كلمات المرور أو hashes أو توكنات الجلسات في الاستجابات.

## اختبارات المصادقة ومعايير الاكتمال

- نجاح الدخول عبر الأنظمة المسموح بها بنفس الهوية، مع توجيه صحيح للعميل وصاحب المتجر والأدمن.
- نجاح Google OAuth وفشل الحالات غير الصالحة: state/nonce/audience خاطئة، انتهاء التوكن، رفض الموافقة، وتكرار callback.
- عدم الاستيلاء على حساب قديم عبر بريد مكرر أو غير موثق؛ معالجة الربط وفكه والتعارض وفق السياسة.
- اختبار التزوير في الدور والـ IDs، والدخول المباشر لمسارات الأدمن، وعزل المتاجر، والحسابات الموقوفة.
- اختبار التجديد والانتهاء والإبطال والخروج الموحد وتعدد الأجهزة وتغيّر الصلاحيات.
- بقاء الحسابات والبيانات والاشتراكات القديمة قابلة للاستخدام أو الاسترداد خلال الانتقال، مع خطة رجوع مختبرة.
- توثيق تدفقات الدخول وعقود الهوية والجلسات والصلاحيات والأسرار المطلوبة دون تسجيل قيمها.

## نقاط تحتاج مراجعة عند التنفيذ

- موفر الهوية النهائي، والدومين المركزي، والدومينات النهائية لـ Hub وStore والإدارة.
- هل توجد Google OAuth app حالية يمكن إعادة استخدامها، ومن يملك إعداداتها؟
- قواعد التحقق من البريد ودمج الحسابات واسترداد الحساب وتسجيل الدخول بكلمة المرور.
- قواعد MFA للحسابات الإدارية، ومدة الجلسات، وسياسة الخروج من جميع الأجهزة.
- كيفية دخول Flow المحلي/سطح المكتب، وحدود عمله دون اتصال، وآلية العودة الآمنة للتطبيق.
- الأدوار الفعلية والصلاحيات القائمة وعدد مصادر الحسابات؛ لم تُفحص الآن.
