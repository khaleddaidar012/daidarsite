# 03 — تكامل Daidar Ecosystem كمنظومة SaaS

## الهدف

ربط Daidar Hub وDaidar Store وDaidar Flow وSuper Admin بمنظومة واحدة للهوية والاشتراكات والصلاحيات، مع الحفاظ على بيانات الأنظمة الحالية وطبيعة عمل كل نظام. لا تفترض المهمة إعادة كتابة الأنظمة أو دمج جميع قواعدها في قاعدة واحدة.

## ربط الأنظمة

### Daidar Hub

- نقطة مركزية لعرض الأنظمة والخدمات المتاحة للعميل واشتراكاته وحالاتها وروابط الدخول الصحيحة.
- عرض ما يملكه المستخدم فعلياً وإجراء الدخول إلى النظام المقصود دون تسجيل متكرر غير لازم أو روابط localhost منشورة.
- الفصل بين واجهة العميل وإدارة المنصة، والحفاظ على وظائف Hub الحالية أثناء الانتقال.

### Daidar Store

- ربط التاجر والمتاجر والاشتراكات بالهوية الموحدة مع الحفاظ على معرّفات وملكية المتاجر والمنتجات والطلبات.
- التفعيل والتعليق والتجديد وفق مصدر الاشتراك المركزي، مع تطبيق العزل والصلاحية على جهة الخادم.
- استمرار روابط المتاجر العامة والعملاء وطلبات واتساب دون اشتراط دخول العميل العام أو تعطلها أثناء Migration.
- اعتماد عقود البيانات الجديدة قبل إعادة بناء واجهة صاحب المتجر في المهمة الأولى.

### Daidar Flow

- ربط العميل والتراخيص والأجهزة واستحقاق استخدام النظام بالهوية والاشتراك الموحدين.
- الحفاظ على بيانات التشغيل المحلية والمخزون والتراخيص القائمة؛ عدم رفع البيانات المحلية أو تغيير سلوكها دون سياسة وموافقة واضحة.
- تحديد سياسة العمل دون اتصال وانتهاء الاشتراك وإلغاء الجهاز والتزامن والتعارض واستعادة الوصول.
- لا تفترض مشاركة جلسة متصفح مع تطبيق سطح المكتب أو تحويله إلى تطبيق سحابي بالكامل.

### Super Admin

- إدارة المستخدمين وعلاقات الحسابات والأنظمة والمتاجر والاشتراكات والأدوار من مساحة إدارية مستقلة.
- تمييز إدارة المنظومة عن صلاحيات صاحب المتجر وعن إدارة موظفي موقع دعيدر الحالية؛ عدم توسيع الوصول بينهما تلقائياً.
- توفير سجل تدقيق للعمليات الحساسة مثل الربط ونقل الملكية وتغيير الدور والتفعيل والتعليق والتجديد، دون تخزين الأسرار في السجل.

## الاشتراكات والهوية والصلاحيات

- اعتماد معرّف مستخدم مركزي وعلاقة واضحة بين المستخدم والمؤسسة/tenant والمتجر والنظام والجهاز حيث يلزم.
- تعريف كتالوج الأنظمة والخطط والاستحقاقات ومدد الاشتراك وحالاته ومصدر القرار النهائي لكل منها.
- دعم الحالات الفعلية: انتظار التفعيل، فعال، منتهي، موقوف أو ملغى، وتجريبي إن كان معتمداً. تحديد أثر كل حالة على القراءة والكتابة والدخول.
- ربط الاشتراكات الحالية دون تغيير الأسعار أو المدد أو أرصدة العملاء تلقائياً. تسجيل المدفوعات يظل وفق الإجراءات المعتمدة؛ لا تفترض تحصيلاً آلياً.
- تعريف الأدوار وقيود الوصول داخل كل نظام وعلى مستوى المنظومة، مع تحقق الخادم من الاستحقاق بدلاً من الاعتماد على إخفاء الأزرار.
- استخدام اتصالات وعقود موثوقة بين الأنظمة وإعادة محاولة آمنة وعمليات idempotent عند تكرار الأحداث أو تأخرها.

## حماية البيانات وخطة Migration

- جرد قواعد البيانات والمخططات والملفات والبيانات المحلية والنسخ الاحتياطية وعلاقاتها، مع تعيين مصدر الحقيقة لكل نوع بيانات.
- أخذ نسخة قابلة للاستعادة والتحقق من الاسترجاع قبل أي Migration حقيقي.
- إضافة المخططات وجداول الربط بشكل تدريجي يحافظ على المفاتيح القديمة والملكية والسجلات التاريخية.
- إعداد تحويل تجريبي على بيانات معزولة، ومطابقة أعداد السجلات والعلاقات والاستحقاقات، وكشف المكرر والتعارض دون حذفه تلقائياً.
- تحديد نافذة الانتقال وأي توقف مطلوب ومسار القراءة/الكتابة خلال الانتقال، وكيفية تجنب مصدرَي حقيقة متعارضين.
- استخدام backfill قابل للاستئناف ونسخ migrations وترتيبها، دون إعادة تنفيذ migrations غير idempotent عشوائياً.
- وضع خطة رجوع واضحة، ومراقبة الأخطاء وتسجيل الربط والتغييرات، وإيقاف التوسع إذا ظهر فقد بيانات أو تجاوز صلاحيات.
- إبقاء التطوير والمعاينة والإنتاج منفصلة، وعدم نسخ بيانات العملاء الحقيقية إلى بيئة عامة دون ضوابط وموافقة مناسبة.

## المراحل والاختبارات ومعايير الاكتمال

1. فحص البنية الفعلية بعد الموافقة وتوثيق المخططات والدومينات والتراخيص والصلاحيات.
2. تثبيت الهوية الموحدة والمصادقة في المهمة الثانية، مع واجهات وعقود متفق عليها.
3. تثبيت نموذج الاشتراكات والاستحقاقات، ثم ربط Hub وStore تدريجياً مع توافق الحسابات القديمة.
4. ربط Flow والتراخيص والأجهزة وسياسة offline بعد اختبار العقود السحابية الأساسية.
5. استكمال Super Admin لإدارة دورة حياة الحسابات والأنظمة والاشتراكات، بالتوازي مع كل شريحة تكامل.
6. تنفيذ واجهة صاحب المتجر فوق العقود المستقرة، ثم اختبار المنظومة كاملة قبل التوسع للإنتاج.

- اختبار رحلة مستخدم واحد من Hub إلى Store وFlow وفق اشتراكاته، ورحلة أدمن مستقلة دون اختلاط الأدوار.
- اختبار عزل tenants وحماية APIs، والتجديد والتعليق والانتهاء والخروج وتغيّر الصلاحيات عبر الأنظمة.
- اختبار فقد الاتصال والأحداث المكررة والمتأخرة وتعارض التزامن وحدود offline في Flow.
- اختبار Migration والرجوع والحفاظ على الطلبات والمنتجات والتراخيص والحسابات والأرصدة/المدفوعات الموجودة إن وجدت.
- اكتمال المهمة يتطلب عقوداً موثقة، وبيانات متسقة، واختبارات تكامل ناجحة، وخطة تشغيل ورجوع قابلة للاستخدام، وعدم وجود فقد بيانات أو صلاحيات زائدة.

## نقاط تحتاج مراجعة عند التنفيذ

- هل المقصود حساب فردي أم مؤسسة متعددة الأعضاء والمتاجر؟ ومن يملك كل مورد؟
- الباقات الفعلية والاشتراكات المجمعة مقابل اشتراك كل نظام وسياسات التجربة والتجديد والإلغاء.
- النطاق الحقيقي لعمل Flow دون اتصال والتراخيص الحالية وصيغها ومسارات التحقق منها.
- مصادر البيانات الحالية والدومينات النهائية والتكاملات والـ webhooks والحدود التشغيلية والتكاليف المقبولة.
- الصلاحيات الدقيقة لكل نوع أدمن وموظف وتاجر، ومتطلبات سجل التدقيق ونقل الملكية.
- شروط الموافقة على تغييرات الإنتاج أو خطوات لا يمكن الرجوع عنها؛ لا تفترضها الخطة تفويضاً مسبقاً.
