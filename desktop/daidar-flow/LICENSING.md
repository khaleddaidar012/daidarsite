# Desktop licensing v1

## Scope and trust
Tasks 11–16 implement activation only. No business modules, installer, online licensing service or Hub license changes. The Hub protocol remains independent: desktop uses product `daidar-flow-desktop`, prefix `DFL1`, and its own Ed25519 trust roots. A Hub license is never accepted here.

The signed envelope is `DFL1.base64url(canonical UTF-8 JSON).base64url(signature)`. Maximum input 16 KiB. Payload fields, in canonical order: v, product, keyId, licenseId, customer, deviceId, issuedAt, startsAt, expiresAt, months, features, replaces. UTC ISO timestamps, 1/3/6/12 calendar months (UTC month-end clamping), explicit paid entitlements. Unknown fields, duplicate/unknown entitlements, bad encoding, wrong product/version and malformed dates fail closed. Main owns verification and checks entitlement at every feature request. Renderer state grants nothing. Future business entry points must call the same guard.

## Identity
Windows MachineGuid + SMBIOS UUID + BIOS serial are normalized and hashed with a domain separator. MAC/network cards, disk, user name and host name are not inputs. At least two usable identifiers are required. Missing/placeholder values are rejected. Hash only is exposed; raw identifiers are not persisted or sent. A protected local snapshot permits temporary probe failure, but a successfully detected hardware/OS identity change blocks activation until administrative reissue. There is no silent reassignment. Same-user restart and network/disk changes preserve identity; motherboard/OS reinstall/VM cloning may change it or duplicate it. Admin review is required for such cases. Cryptographic device binding is an exact match, not a fuzzy authorization rule.

## Keys and administrator workflow
The independent Node/Windows admin CLI generates Ed25519 keys and protects private PKCS8 material with Windows DPAPI CurrentUser in an external admin vault. Private keys never enter the client build or Git. Public SPKI trust roots alone are checked in. Back up the vault with a protected Windows account/system backup; keep it on the admin machine only. Losing the key requires a new public-key client release. Additional public roots allow planned rotation. There is no renderer or environment override for trusted keys.

Issue: collect copied Device ID, choose customer/duration and optional start date, write signed .dfl file, record external ledger. Reissue: verify a previously issued ledger license, require a new Device ID, administrative reason and explicit transfer confirmation, record the replacement relationship; preserve original subscription dates. Prevent repeated transfer of a superseded record. Offline old clients cannot be remotely revoked: collect/deactivate old installation as an administrative requirement; immediate guaranteed revocation needs an online revocation service. Never promise simultaneous-seat prevention offline.

## Local persistence and time
Client stores the signed code, device snapshot, last-seen UTC high-water mark and a sticky clock-review flag in an atomically replaced DPAPI-protected state file under Electron userData. No plaintext fallback. Missing first-run state is free; corrupt/unreadable state blocks paid access. Free cards always remain usable. No business records are written or deleted by licensing. Single-instance lock prevents concurrent state writers.

Check expiry on every operation and refresh the UI periodically and on focus. Effective time never decreases: max(wall UTC, prior high-water, session monotonic elapsed). Rollback exceeding five minutes sets sticky clock-review; paid features remain locked until clock catches up to saved time. Importing a new license does not clear clock/storage/device problems. Expiry at the exact endpoint locks paid only. Warning/countdown begins five days (120 hours) before expiry. Wall-clock forward jumps may expire early; changing the clock back cannot revive it. Manual OS clock repair may require admin review.

Offline limits: a local administrator can patch a binary, spoof identifiers, clone a VM, delete all state, or restore a complete old snapshot with its old clock. DPAPI protects at rest across Windows users, not from arbitrary code already running as the same user. These controls are basic tamper resistance, not an offline trusted clock or unbreakable DRM. Stronger revocation/time requires a future authenticated service and signed timestamps. Install signing/fuses/update integrity remain installer-stage work; no obfuscation-based guarantee.
